Your client list, your contracts and three years of invoices are the memory of your business. Most freelancers keep that memory in software they rent and can't see inside. That usually works fine, until the price doubles, a feature you rely on disappears, or the company is sold. Open-source software gives you another option. Here is why it matters for a small service business, what to look for, what self-hosting really costs you in time, and how Thrive handles both sides.

Why open source matters for a small business

Open source means the code is public and published under a licence that lets anyone use, change and run it. For a freelancer that is less about ideology and more about five practical protections.

You own your data

With open-source software you can always see how your records are stored, and nothing stops you from running a copy where you control the database. Your clients and invoices don't depend on one company's goodwill.

No lock-in

If you outgrow the tool, or just want to leave, the format of your data is documented in the code itself. Moving on is a project, not a hostage negotiation.

You can host it yourself

If you want to, you can run the software on your own accounts. Some freelancers do this for privacy, some for cost, some because a client contract requires it. Most never do, but having the option changes the relationship with the vendor.

You can inspect the code

You, a developer friend or a client's security team can read how a link is shared, what a client can see and where a file is stored. You don't have to take a marketing page's word for it.

The price can't be held hostage

A hosted plan can still go up. But when the software itself is free to run, the vendor knows you can leave and take the same tool with you. That keeps prices honest. For a freelancer who has built five years of processes around one app, this is the most underrated benefit.

What to look for

"Open source" on a homepage is a start, not a guarantee. Before you commit your business to a tool, check these points:

  • The licence. Permissive licences such as MIT let you use, change and host the software for any purpose, including commercial work. Some "source-available" licences restrict that, so read the licence file.
  • The code is actually public, in a repository you can open, not "available on request".
  • Self-hosting docs exist and describe a real production setup, not just a local demo.
  • You can export your data from the hosted version too, in a format like CSV.
  • The hosted version is the same software. If the paid cloud has features the open code doesn't, you are back to lock-in.
  • It does the job. Open source doesn't make up for missing features. Check the proposals, contracts and invoices work the way you do.
  • It is still maintained. Look at when the code last changed and whether updates come with instructions.

The honest trade-offs of self-hosting

Hosting your own business software is a real responsibility. Before you choose it, be clear about what you are signing up for:

  • You maintain it. Updates, backups and fixing things when a provider changes something are your job. Nobody else is watching your copy at 2 am.
  • You need accounts with infrastructure providers. For Thrive, that means a Cloudflare account and a Supabase project. Their plans and usage costs are between you and them.
  • You need some technical comfort. You will use a terminal, edit a configuration file, set secrets and read error messages. If "run npm test" sounds unfamiliar, the hosted version is probably the better choice.
  • Backups are on you. Your invoices and signed contracts are business records. A copy you can't restore isn't a backup.
  • Email and calendar take extra setup. Connecting mailboxes and calendars usually needs your own accounts with a provider, plus their review processes.

For most freelancers, the sensible path is: use the hosted version, and value the fact that you could self-host if you ever needed to.

Self-hosted: free under the MIT licence

You can run the same code on your own accounts. Thrive's self-hosting guide (docs/self-hosting.md in the repository) describes a setup on Cloudflare Workers with Supabase for sign-in, the database and private file storage. In short:

  1. Create a Supabase project and apply the SQL migration files from the repository once, in order. Turn on email and password sign-in, set your site address and redirect URLs, and configure your own SMTP service for sign-up and password emails.
  2. Configure the Worker. With Node.js 22.13 or later, install and run the tests, then set your Worker name, your app's address and your Supabase URL in wrangler.self-hosted.jsonc.
  3. Build and deploy with Wrangler, then add your two Supabase keys as Worker secrets. Use the Worker's own workers.dev address or attach your domain.
  4. Optional extras. Email, calendar and booking pages need your own Nylas account. To connect Claude or ChatGPT, enable Supabase's OAuth server as the guide describes.
  5. Verify and back up. The guide includes a checklist: sign-up and sign-in, data saved across browsers, client links that stop working when revoked, and backups of both the database and stored files.

The repository also includes a setup prompt you can hand to a coding agent to walk through the installation with you. A self-hosted copy works for one person, or for several people with separate workspaces; there is no shared-team permissions model. Billing is off in a self-hosted install.

A quick decision checklist

  • Do you want to spend time on updates and backups? If not, use the hosted version.
  • Does a client or your own privacy policy require data on your accounts? Self-host.
  • Are you comfortable with a terminal and configuration files? Self-hosting is realistic.
